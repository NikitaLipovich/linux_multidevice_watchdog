# CONFIG_REFERENCE — /etc/svc_watchdog.conf, каждый параметр

> Единый источник истины для C-демона (`svc_watchdog`) И Python-стороны (`run_services.py`/`wd_runtime.py`/`wd_beat.py`).
> Колонка «Кто» — кто читает. Колонка «Боевое» — текущее боевое значение (НЕ дефолт: дефолтов больше нет).
>
> **FAIL-CLOSED (v1.2, решение пользователя):** дефолтов в коде НЕТ. Каждый читаемый ключ ОБЯЗАТЕЛЕН.
> Нет файла / битый JSON / нет ключа → C-демон: `stderr "missing key <путь>"` (ВСЕ пропуски разом) + exit 1;
> Python: `FATAL run_services: ... missing key(s): ...` в stderr/logread + exit 1, НОЛЬ сервисов
> (procd владеет respawn'ом и троттлит). Единственное исключение из «громко» — `wd_beat.beat()`:
> он на горячем пути каждого цикла и по контракту never-raises (без конфига молча не шлёт;
> процесс с битым конфигом всё равно не стартует).
>
> Валидаторы при старте C: все ключи присутствуют; строки влезают в буферы (длиннее = ОТКАЗ, не
> усечение); `action`/`mode` только из словаря; `wait_pulse_timeout_ms ≥ 3×beat_interval_ms`;
> `min_free_mb > rut_floor_mb`; `progress_stall_ms ≥ 0`; `after_attempts ≥ 1`; `services[]` непуст,
> >30 записей = ошибка (не молчаливый пропуск).
>
> **Где лежит конфиг:** `/etc` на этом боксе = overlayfs, upperdir на SD `/dev/sda1` (extroot,
> проверено фактом: `mount | grep overlay`). Физически файл живёт на флешке, переживает ребут,
> RAM не ест. В /tmp (tmpfs=RAM) — только нулевые файлы-флаги: сокет, pidfile, wd_pause,
> crash-файлы, тест-хуки.
>
> **Статические ёмкости C (compile-time, согласованы):** `MAX_SERVICES=30` (~12КБ статики),
> `NAME_MAX_LEN=48`, `STATE_MAX_LEN=24`, `PATH_MAX_LEN=256` — буферы строк svc_t/cfg_t (malloc'а
> в демоне нет); значение длиннее буфера = отказ старта. Приёмный буфер датаграммы 128Б
> (худший легальный пульс: имя47 + " active "8 + int64-счётчик20 = 75Б; длиннее — ядро усечёт,
> имя уйдёт в unknown_name).

## Корень

| Параметр | Кто | Боевое | Смысл |
|---|---|---|---|
| `socket` | оба | /var/run/svc_wd.sock | unix-datagram, куда сервисы шлют пульс (tmpfs — ок, это IPC) |
| `beat_interval_ms` | Python | 5000 | период базового пульса каждого сервиса. Связка: таймауты сервисов ≥ 3× этого |
| `tick_ms` | C | 1000 | период проверки таймаутов (timerfd). Меньше — быстрее детект, больше просыпаний CPU |
| `pause_file` | C | /tmp/wd_pause | файл существует → wd только логирует `paused`, НЕ действует. Ручной предохранитель на время работ |
| `self_oom_adj` | C | -1000 | oom_score_adj самого wd: неубиваем для kernel-OOM |
| `paused_log_every_ms` | C | 60000 | как часто напоминать в лог, что стоим на паузе |
| `unknown_name_log_every_ms` | C | 60000 | rate-limit строк `unknown_name` (датаграммы с чужим именем) — защита лога от флуда. 0 = логировать каждую (нужно тестам ротации) |

## `log` — крэш-лог wd (внешний взгляд)

| Параметр | Кто | Боевое | Смысл |
|---|---|---|---|
| `file` | C | — | путь лога. ОБЯЗАТЕЛЬНО на SD (НЕ /tmp=tmpfs): цель — читаться через неделю после ребута |
| `max_bytes` | C | 1048576 | порог ротации (1МБ) |
| `keep` | C | 7 | сколько ротаций хранить (≈неделя) |
| `fsync` | C | true | fsync на каждую строку: последние строки переживают SIGKILL/OOM. События редки — SD не страдает |

Каждая строка: `<wall-дата> up=<монотонные_сек> <событие> k=v…`. `up=` обязателен для чтения порядка: wall-clock на боксе прыгает (time_sync/RTC).

## `resources` — «здоровы ли ресурсы?» перед КАЖДЫМ рестартом

| Параметр | Кто | Боевое | Смысл |
|---|---|---|---|
| `rut_floor_mb` | C | 5 | НЕПРИКОСНОВЕННЫЙ минимум RutOS (SSH/модем живы). Ниже → строка `mem_below_floor` (сигнальная линия; действий v1 не делает) |
| `min_free_mb` | C | 8 | порог ДОСТАТОЧНОСТИ для рестартов = floor + цена самого рестарта (~2-4МБ пик). Ниже → ждём, не рестартим. Должен быть > floor (валидатор) |
| `max_load1` | C | 3.0 | loadavg(1m) выше → ждём |
| `recheck_ms` | C | 5000 | шаг перепроверки, пока ждём (`waiting_resources` в лог не чаще этого) |
| `max_wait_ms` | C | 300000 | ждали 5 мин и всё плохо → рестартим ВСЁ РАВНО (мёртвый сервис сносится — рестарт обычно память освобождает) |

## `restart_delay` — пауза МЕЖДУ попытками одной цели (2 режима на выбор)

| Параметр | Кто | Боевое | Смысл |
|---|---|---|---|
| `mode` | C | fixed | `fixed` = тупо раз в interval_ms (предсказуемо); `backoff` = растущая пауза (не долбить сломанное) |
| `interval_ms` | C | 5000 | [fixed] период попыток |
| `initial_ms` / `factor` / `max_ms` | C | 2000 / 2 / 60000 | [backoff] initial×factorⁿ до потолка; успешный pulse_back сбрасывает счёт |

Фактическая пауза после СЪЕДЕННОГО crash-файла = max(это, `service_relaunch_ms`).

## `process` — политика процесса «unified»

| Параметр | Кто | Боевое | Смысл |
|---|---|---|---|
| `name` | C | unified | имя (для логов) |
| `initd` | C | — | ЕДИНСТВЕННЫЙ способ рестарта процесса: `fork/exec "<initd> restart"`. Сами НЕ сигналим никогда (гонка с procd-respawn) |
| `pidfile` | C + launcher | /tmp/rut_services.pid | пишет launcher (`echo $$` перед exec), причём путь launcher ЧИТАЕТ из этого же ключа через jsonfilter (v1.2: раньше был захардкожен вторым экземпляром — разъезд слепил fresh-гейт). Кормит **fresh-гейт**: процесс моложе `start_grace_ms` → это procd только что переродил его (kill -9/OOM) → полный grace, никаких действий (`fresh_process_detected`) |
| `crash_file_template` | оба | /tmp/svc_crash_{name} | рестарт сервиса = creat(шаблон); супервизор поллит и пересоздаёт. Весь путь здесь, в коде префикса нет |
| `consume_timeout_ms` | C | 10000 | crash-файл НЕ исчез за это время → супервизор мёртв → эскалация в рестарт процесса |
| `service_relaunch_ms` | C | 60000 | окно ПЕРЕЗАПУСКА: файл съеден → фабрике сервиса дают раскрутиться (data_uploader ~34с) до следующей попытки. Без него свежий файл ложится под занятый супервизор → ложная эскалация |
| `start_grace_ms` | C | 90000 | после (ре)старта процесса пульсы не проверяем. Должен покрывать stop(≤10с)+boot(~35с)+первый пульс с запасом |
| `soft_fail_escalation.enabled` | C | true | глобальный тумблер митигации «Б» (v1.2: секция ОБЯЗАТЕЛЬНА — «нет секции = выключено» больше не существует) |
| `soft_fail_escalation.after_attempts` | C | 3 | N мягких попыток ПОДРЯД без pulse_back = «мягкий рестарт не лечит» |
| `action` | C | restart | `restart` \| `log` — реакция на no_pulse_all (вис loop). `log` = observe-режим всего демона |

## `python` — калибровки Python-стороны (читает wd_runtime.py; run_services.py — только через него)

| Параметр | Боевое | Смысл |
|---|---|---|
| `activity_tick_ms` | 2000 | **v1.2**: единый период L2-тика флеш-пути — И троттлинг датаграмм `_WdActivity.tick()` (flash.py), И длина среза пере-взвода recv в клиентах odrive_fw/vesc_fw (клиенты конфиг НЕ читают — число приходит аргументом `activity_tick_s`; протокол/суммарные таймауты не зависят от него). Связка: `progress_stall_ms(config_server)=60000 ≥ 30×` этого |
| `config_server_port` | 8000 | **v1.2**: единственная точка истины порта config_server — его читают bind фабрики И TCP-самопроба пульса (раньше литерал 8000 жил в 3 местах run_services.py) |
| `teardown_timeout_ms` | 20000 | потолок уборки сервиса: зависший teardown не должен заклинить супервизор |
| `probe_timeout_ms` | 2000 | таймаут TCP-самопробы пульса config_server (порт реально отвечает → бьёмся) |
| `http_shutdown_timeout_ms` | 5000 | aiohttp: добивание открытых соединений при уборке (дефолтные 60с вешали мягкий рестарт) |
| `crash_poll_ms` | 1000 | как часто супервизор проверяет crash-файл (≪ consume_timeout_ms!) |
| `supervise_backoff` {initial_ms,factor,max_ms} | 1000/2/10000 | бэкофф супервизора между пересозданиями упавшего сервиса |
| `log` {file,max_bytes,keep} | unified.log/1МБ/7 | лог Python-слоя (traceback'и, `[supervisor] start #N`) — та же папка, что wd.log: одна точка чтения через неделю |

## `services[]` — реестр (что поднимать и как следить)

| Параметр | Кто | Боевое | Смысл |
|---|---|---|---|
| `name` | оба | — | имя = ключ всего: пульс, crash-файл, лог. Лимит 30 записей (≈12КБ статики в C) |
| `entry` | Python | — | `"модуль:функция"` — launcher поднимает через importlib. НОВЫЙ сервис = строка тут + его код; run_services.py не правится. Битый entry → громкий отказ ЭТОГО сервиса, соседи живут |
| `wait_pulse_timeout_ms` | C | 15000 | тишина дольше → тревога. ≥3×beat_interval (потерянная датаграмма ≠ тревога). config_server щедрее (30с — занятость при флеше) |
| `action` | C | restart | `restart` = crash-файл; `log` = только фиксировать (обкатка нового сервиса / опасный рестарт) |
| `escalate_to_process` | C | true | разрешение митигации «Б» ЭТОМУ сервису: после after_attempts неудач — можно ли рестартнуть ВЕСЬ процесс. Логика выбора: teardown доказан soak'ом → false; не доказан → true (страховка) |
| `progress_stall_ms` | C | 0 | **L2 (v1.1)**: state=active И 3-е поле пульса (liveness-счётчик рабочего цикла) не менялось дольше этого → `stalled` → обычная цепочка действий сервиса. **0 = выключено** (и предохранитель: некуда воткнуть тик → не включай). Счётчик = «поток жив и крутится», НЕ прогресс: «устройство молчит» ловят таймауты самого клиента. Эпизод: открывается первым counter-пульсом, закрывается сменой state (flash.py шлёт `idle` в finally) или рестартом. config_server=60000 (тики ≤2с → запас 30×) |

## Контракты вне конфига (обязательства кода)
- Пульс сервиса живёт в ЕГО собственном цикле и бьётся ПЕРВЫМ действием при старте (иначе гонка с попытками wd).
- Teardown сервиса убирает всё СВОЁ (задачи+порты); фабрика атомарна (упала — прибрала за собой).
- Тест-хуки: `/tmp/wd_test_mute_<name>` (заглушить пульс), `/tmp/wd_test_hang` (вис loop 90с).

## Диаграмма принятия решений (граф зашит в C; все числа/режимы — из конфига; v1.1)
```
tick: floor-сигнал → pause? стоп → grace? стоп → fresh-процесс? grace+стоп
  → ВСЕ тихие? [no_pulse_all → observe? стоп → delay → ресурсы → PROCESS_RESTART]
  → иначе per-S: ТРИГГЕР = no_pulse ИЛИ stalled(L2: state=active И счётчик замер > progress_stall_ms(S))
       → жив и не stalled? [pulse_back / progress_back → сброс попыток] → дальше ничего
       → action=log? только лог
       → файл создан? [съеден → окно relaunch (+stall-рестарт: полный сброс эпизода)
                       | висит>consume → эскалация: ГЕЙТ process.action=restart → PROCESS_RESTART (observe = только лог, фикс v1.1)]
       → attempts≥after_attempts? [process.action=restart И enabled И esc(S) → PROCESS_RESTART(soft) | иначе только лог]
       → delay/relaunch → ресурсы → creat(crash-файл)
датаграмма: "<имя> [<state> [<counter>]]" → last_seen/state/pulse_back+сброс;
  смена state → эпизод L2 закрыт; counter изменился → last_progress=now; чужая → unknown_name (rate-limit)
```
Менять числа/тумблеры = конфиг; менять ПОРЯДОК ветвей = перекомпиляция (осознанно: «тупой» демон; конфигурируемый граф = META_LAYER из бэклога).
