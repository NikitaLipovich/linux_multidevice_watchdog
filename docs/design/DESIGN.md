# DESIGN.md — watchdog v2: оси изменчивости, границы слоёв, отвергнутые альтернативы

## Проблема и не-цели

Библиотека супервизии сервисов + тонкий демон-наблюдатель, поведение целиком из конфига
(`svc_watch.conf`, схема в CONFIG_V2_DRAFT.md). НЕ цели: распределённый мониторинг, метрики,
конфигурируемый ПОРЯДОК ветвей решения (граф решений — компиляция, осознанно «тупой» демон).

## Потребители (доказательство универсальности)

- **A — боевой RUT**: C-наблюдатель + python-процесс unified (4 сервиса) на RUT956.
- **B — in-memory harness**: та же библиотека без ОС (транспорт/probe/действия в памяти,
  время симулировано) — доказывает, что core не прибит к unix/procd/файлам.
- **C — стресс дизайна**: второй процесс на боксе (описан конфигом, см. пример в DRAFT) —
  ломает допущение «процесс один»: группы P-уровней и адресные рестарты обязаны работать.

## Оси изменчивости (кто меняется независимо от кого)

| Ось | Стабильный механизм (core) | Переменная политика (конфиг) | Точка расширения (адаптер) |
|---|---|---|---|
| Доставка сигналов | таблица last_seen, эпизоды | socket/format | transport: unix_datagram, udp, inmemory |
| Доказательство пульса | «probe перед emit» | every_ms, timeout, port | probe: tcp, http, custom_callable |
| Старт сервиса | супервизор-цикл, изоляция падений | entry, backoff | start: python_factory, external_command, inmemory |
| Воздействие | лестница, tries, pacing, gates | состав лестниц, параметры действий | action: request_file, init_script, run_command, inmemory |
| Суждение | уровни L1/L2/P1/P2, пороги-сравнения | dead_after/frozen_after/mode | новый уровень = пара signals.X + watch.* (+core) |
| Топология | группировка по процессам | processes{} ⊃ services{} | блок конфига |

## Границы слоёв (lib_py/svc_watch)

- `contracts.py` — протоколы: `Transport.emit(msg) [never-raises]`, `Probe() -> bool`,
  `StartMechanism.create()/teardown adapter`, `ActionExecutor.execute(target)`.
- `core.py` — машина здоровья: сигналы → уровни → лестницы; счётчики tries; выздоровление
  = ступень 0; НИ ОДНОГО имени сервиса/пути/порта/ОС-вызова (проверяется грепом в Э2 DoD).
- `config.py` — схема/парсер/валидатор (fail-closed, все проблемы разом, @-резолв) — не исполняет.
- `adapters/` — всё, что трогает ОС или конкретную технологию; inmemory-набор для B.
- `runtime.py` — composition root: валидированная модель → собранные объекты
  (`emit_signals(service)`, `supervise_process(name)`).
- Примеры (examples/) — тонкие: unified_rut (A) и inmemory_demo (B).

## Порядок суждения наблюдателя (семантика ядра — НЕ конфиг)

Тик: floor-сигнал → pause-файл → grace (в т.ч. fresh-гейт по возрасту pidfile В НАЧАЛЕ) →
P-уровни каждого процесса (P1 все-молчат, P2 запрос-завис) → L-уровни каждого сервиса
(жив → сброс лестниц/лог выздоровления; иначе лестница уровня: pacing → gates → действие).
Исполнение process-действия: grace процессу + полный сброс состояний его сервисов.
Наследовано из v1.2 дословно (порядок ловил реальные гонки: fresh-гейт против procd-respawn,
окно startup_ms против медленных фабрик) — см. TRACE_V1_TO_V2.md, колонка CORE.

## Отвергнутые альтернативы (и почему)

1. **YAML/TOML/UCI/кастомный DSL вместо JSON** — на RUT резидентен только libjson-c;
   новая зависимость или рукописный парсер на реliability-critical демоне не оправданы.
   Читаемость добита структурой (карты-по-имени, @, короткие ключи) и jsonc-эталоном в DRAFT.
2. **truth_check как отдельный уровень L1.5** (итерации 2–3) — породил `type:"none"`-заполнитель;
   проверка — свойство ИСТОЧНИКА пульса (from:"probe"), невыразимость вместо правила.
3. **enabled-флаг у L2 с мёртвыми параметрами** — заменён парностью наличия
   `signals.activity ⟺ watch.L2_activity_frozen` (+mode log для обкатки живого сигнала).
4. **«действие провалилось → следующая ступень лестницы сервиса»** (итерация 4) — ложная
   адресация: незъеденный запрос = болезнь ПРОЦЕССА (супервизора) → процессный уровень
   P2_request_stuck (найдено обходом v1.2, TRACE §1).
5. **Тройной гейт эскалации** (process.action × enabled × per-service флаг, v1.2) — заменён
   составом лестницы + observer.mode: право = наличие ступени; предохранитель один.
6. **Плоский services[] с обратной ссылкой на процесс** (итерация 1–2) — вложение показывает
   принадлежность структурой; валидатору меньше ссылок, глазу не нужно резолвить.
7. **Один beat_interval на всех** (v1.2) — период пульса = свойство сервиса (per-service
   every_ms); боевые значения пока одинаковы.
8. **http_shutdown_timeout в вотчдог-конфиге** (v1.2) — калибровка aiohttp-фабрики, не
   наблюдения; уходит в код потребителя A (вотчдог-конфиг не свалка чужих настроек).

## Миграция и совместимость

v1.2 остаётся боевой до конца Э5. Схема v2 несовместима по формату (schema=2, новый путь
/etc/svc_watch.conf) — миграция = деплой пары (демон v2 + конфиг v2) атомарно, откат =
пара v1.2 (бинарь+конфиг сохранены). Протокол датаграмм text_v1 обратно совместим
(тот же формат, что v1.1/v1.2) — сервисы можно переводить на новую библиотеку поэтапно.

## Итерация 6 — улучшения структуры (ревью «зная структуру»)

1. **Каталог `ladders`** — лестница = переиспользуемая политика; уровень выбирает `"@имя"`
   (инлайн-массив остаётся для одноразовых). Убивает дублирование политики по сервисам
   (дрейф при правке в N местах); «подключать и выбирать» действий/политик — буквально.
2. **Правило ядра для P1**: судится только при ≥2 сервисах процесса — при единственном
   сервисе «все молчат» неотличимо от его L1 (нашлось стресс-тестом потребителя C:
   vision с одним camera_feed получал бы рестарт процесса вместо мягкого recreate).
   Эскалацию одно-сервисного процесса несут лестница его L1 + уровень P2. Валидатор
   предупреждает (правило 11).
3. **Валидатор ужесточён**: неизвестный ключ = отказ (опечатка `"trys"` не может молча
   игнорироваться); rate-limit'ы ≥ 1мс (вырожденный 0 запрещён); шаблоны request_file
   уникальны.
4. **Контракт StartMechanism**: фабрика получает валидированную модель СВОЕГО сервиса
   (name, port, signals) параметром от runtime — не читает конфиг сама, не тянет глобалок.
   (Иначе Э2 неизбежно изобрёл бы обратную зависимость сервис→конфиг.)
5. **Рассмотрено и отвергнуто (в итер.6, ПЕРЕСМОТРЕНО в итер.8 — см. ниже)**: контекстный
   рестарт процесса. Тогда отверг «магию контекста» в пользу явной ссылки. Ревью дизайна
   показало: явная ссылка `@restart_unified` из ОБЩЕГО каталога лестниц порождает кросс-
   процессный промах (сервис чужого процесса эскалирует не туда) И ломает переиспользуемость
   каталога. Баланс сместился → принят контекст-глагол (итер.8).
   per-step переопределение pacing/gates (нет показанной изменчивости — аддитивно потом).

## Итерация 8 — адверсариальное ревью дизайна (24 находки пережили проверку)

Пять независимых линз (abstraction / потребители B,C / шов C↔py / валидатор / регрессия)
+ адверсариальная проверка каждой находки на опровержение. Ключевое:

1. **Кросс-процессный промах (3 линзы независимо — сильнейший сигнал).** `escalate_std`/
   `restart_process` зашивали `@restart_unified`; валидатор не проверял, что рестарт-процесса из
   watch сервиса S целит в S. → **ПЕРЕСМОТР отказа №5**: рестарт процесса стал встроенным глаголом
   `restart_process` (без `@`), резолвится в процесс-владелец из контекста вложения. Промах
   структурно невыразим, `escalate_std` реально переиспользуема. `restart_unified` удалён из
   actions; механизм+лимит рестарта → `launch.type`/`launch.restart_rate_limit`. FR-38.
2. **Мёртвый блок `pacing`** (mode+оба варианта — тот самый паттерн, что зарубил `truth_check:none`,
   но проскочивший из v1.2) → типизирован как grace. **`transport`** аналогично (params под type).
3. **`tries`-валидатор без дома**: TRACE утверждал перенос v1.2-урока, но правила не было —
   вырожденная лестница делала эскалацию недостижимой (тот класс сбоя, что лестница лечит). → правило 15.
4. **`recreate.rate_limit` был инертен** (max=20 недостижим при startup_ms-каденции) → max=6 +
   правило достижимости. **Py-супервизор без сдачи** → `max_consecutive_start_failures` (FR-37).
   **`on_exceeded:"stop"`** мог обездвижить бокс → запрещён на процесс-рестарте.
5. **Fail-closed доужесточён**: глобальная уникальность имён (датаграмма без квалификатора
   процесса), закрытое множество watch-уровней, ёмкости коллекций C, `until_ready` требует
   ready-сигнала, `unknown_ms:0` запрещён, `poll_ms ≤ eat/5` машинно-проверяемо.
6. **Контракты (Э2)**: `emit` не только never-raise, но и thread-safe (звался из executor-потоков) — FR-11.

Отвергнуто/понижено ревью же: `activity` обновляет L1 минуя probe — BY DESIGN (исполняемая работа
доказывает жизнь сильнее порт-пробы; probe нужен только пульсу `from:"probe"`), задокументировано.
Ресурсный гейт без типизированного адаптера — он C-сторонний, потребитель B его не гоняет (граница).

## Известные границы (осознанные, аддитивно расширяемые)

- Несколько activity-сигналов у одного сервиса (два worker-пула) — сейчас один;
  расширение: парные имена `signals.activity_X` ⟺ `watch.L2_X_frozen`.
- Процесс без супервизора (внешний демон, только наблюдение) — потребует ослабить
  обязательность `supervisor{}` и start-тип `managed_externally`.
- Per-ladder-step переопределения pacing — добавится полем ступени при доказанной нужде.
- Типизированный ResourceSampler для гейтов (чтобы потребитель B гонял и гейт-путь) —
  сейчас гейты C-сторонние, B их не касается; добавится при нужде.
- Ready-сигнал процесса (`<process> ready`) для `grace.until_ready` — форма в PROTOCOL есть, эмиссия Э5.
