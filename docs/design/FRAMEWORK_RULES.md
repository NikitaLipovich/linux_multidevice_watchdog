# FRAMEWORK_RULES — правила фреймворка svc_watch (проверяемые)

> Формат: `FR-N · MUST/MUST NOT · формулировка · источник · как проверяется`.
> Источник: v1.x = наш оплаченный опыт (гол/файл); ext = внешний аналог (RESEARCH_NOTES).
> «как проверяется» — тест / греп / ревью на этапах Э1–Э6.

## A. Жизненный цикл потребителя (что зовёт код, использующий библиотеку)

- **FR-1 · MUST** · Потребитель собирает систему ТОЛЬКО через `runtime.py` из
  провалидированной модели конфига; фабрики/адаптеры напрямую он не конструирует.
  · v1.2 (run_services.py = тонкий каркас) · ревью: examples/* не импортируют adapters/ напрямую.
- **FR-2 · MUST** · Точка входа процесса: `load_config → (fail-closed) → build → run`.
  Битый/неполный конфиг = громкий отказ + ненулевой код возврата, НИ ОДНОГО сервиса.
  · v1.2 (fail-closed) · тест invalid_config: процесс не стартует, exit≠0, причина в stderr.
- **FR-3 · MUST** · Фабрика сервиса получает провалидированную модель СВОЕГО сервиса
  (name, port, signals-спека) ПАРАМЕТРОМ; конфиг сама не читает, глобалок не заводит.
  · итер.6 · греп: в фабриках нет чтения конфига/глобалей рантайма.
- **FR-4 · MUST** · Первый pulse сервиса уходит ПЕРВЫМ действием после старта (до любой
  работы) — иначе гонка с попытками наблюдателя (crash-файл каждые pacing до первого пульса).
  · v1.2 (udp_logger/data_uploader «first beat immediately») · тест: пульс в пределах < dead_after.

## B. Конкурентность

- **FR-20 · MUST** · Супервизор ВЛАДЕЕТ всеми задачами своего сервиса; при teardown отменяет
  их детерминированно; ни одной дрейфующей/сиротской задачи после остановки.
  · v1.2 G3 (GC-ловушка monitor-task) + ext trio nursery · тест: после N рестартов число
  задач loop не растёт (asyncio.all_tasks стабильно).
- **FR-21 · MUST NOT** · НЕ создавать несопровождаемые `create_task` без сильной ссылки,
  живущей ровно столько же, сколько сервис (слабая ссылка → сборка GC → мёртвый пульс).
  · v1.2 G3 finding #1 · греп: каждый create_task присвоен полю/возвращён как ресурс.
- **FR-22 · MUST** · core берёт ВРЕМЯ инъекцией (`clock()`), НЕ зовёт `time.monotonic()`
  напрямую — иначе потребитель B (симулированное время) невозможен.
  · потребитель B + ext trio · греп: в core.py нет `time.`/`asyncio.sleep` без инъекции;
  тест: core проходит сценарий на fake-clock без реального сна.
- **FR-23 · MUST** · Один event loop на процесс; блокирующая работа (gzip и т.п.) — только
  в executor, НЕ в loop. · v1.2 (io_executor) · ревью.

## C. Ошибки (поверхности never-raise vs fail-closed)

- **FR-10 · MUST** · КОНФИГ fail-closed: отсутствие/битость/неизвестный ключ/битая @-ссылка =
  громкий отказ на СТАРТЕ, все проблемы одним списком. · v1.2 · тесты invalid_config.
- **FR-11 · MUST** · Горячий путь эмиссии сигнала (`emit`) НИКОГДА не кидает И потокобезопасен
  при КОНКУРЕНТНЫХ вызовах из нескольких потоков (event loop + executor-потоки флеша): нет сокета/
  слушателя → сигнал молча теряется, код сервиса не задет. · v1.2 (wd_beat.beat never-raises,
  звался из executor-потоков) + ext sd_notify (no-op вне systemd) + ревью-итер.8 · тест: emit без
  слушателя не бросает; параллельные emit из N потоков без гонки/исключения.
- **FR-12 · MUST** · Падение ОДНОЙ фабрики/сервиса изолировано: соседи стартуют/живут; битый
  entry валит только свой сервис (громкий лог). · v1.2 (supervise_all) · тест: 1 битый entry из N.
- **FR-13 · MUST** · Фабрика АТОМАРНА: если после bind порта что-то падает, фабрика сама
  освобождает порт (иначе осиротевший слушатель = «address in use» навсегда).
  · v1.2 G-findings (порт 1111 data_uploader) · тест: фабрика, падающая после bind, не оставляет порт.
- **FR-14 · MUST** · teardown СЕРВИСА освобождает ВСЁ своё (порты + задачи), BOUNDED по времени
  (`stop_timeout_ms`): зависший teardown не клинит супервизор. · v1.2 G4 + ext k8s preStop ·
  тест: teardown с висящей корутиной прерывается по таймауту.

## D. Сигналы (эмиссия и владение)

- **FR-15 · MUST** · pulse шлёт САМ исполняющийся код потока сервиса (свой цикл — `from:loop`,
  или библиотечная корутина с probe — `from:probe`); внешний «тикальщик» запрещён — он тикал бы
  и у задеадлоченного потока. · v1.1 (разбор с пользователем) · ревью.
- **FR-16 · MUST** · L2-`tick` передаётся рабочему коду ПАРАМЕТРОМ (значение из
  `signals.activity.tick_ms`); рабочий код конфиг/wd не импортирует (живёт и вне бокса).
  · v1.1 (activity-callback в клиенты) · греп: клиенты не импортируют wd/конфиг.
- **FR-17 · MUST** · Рабочий код шлёт `idle` в `finally` рабочей операции — смерть без idle
  оставляет счётчик замёрзшим при active → L2 срабатывает (желаемое). · v1.1 · тест эпизода.
- **FR-18 · MUST** · Пробу перед пульсом (`from:probe`) проваленную → пульс НЕ слать (не врать);
  молчание поймает L1. · v1.2 G3 (ложно-живой пульс config_server) · тест.

## E. Супервизия

- **FR-30 · MUST** · Терминальное повторяющееся действие ОГРАНИЧЕНО: N исполнений по одной цели
  за окно T → cooldown (резко реже) + отдельный аларм в лог; бесконечного долбления нет.
  · ext OTP intensity + supervisord startretries + tenacity stop · тест: >N рестартов за T →
  переход в cooldown, аларм-строка. → конфиг `actions.*.rate_limit` (GAP-1).
- **FR-31 · MUST** · Время слепоты после старта процесса ограничено, но может кончиться РАНЬШЕ
  по событию готовности; при отсутствии события — по верхней границе времени.
  · ext sd_notify READY + k8s startupProbe · тест: ready-сигнал кончает grace до max_ms.
  → конфиг типизированный `launch.grace` (GAP-2).
- **FR-32 · MUST** · «Сервис поднялся» = прожил `min_stable_ms` после старта; смерть раньше =
  как упавшая фабрика (backoff), не «успешный старт». · ext supervisord startsecs · тест:
  сервис, умирающий через <min_stable, идёт в backoff, а не считается up. → конфиг (GAP-3).
- **FR-33 · MUST** · Действие исполняется только под ресурсным гейтом (`gates`); при голодании
  ждать, но force после `force_after_ms` (голодание само не проходит, рестарт освобождает).
  · v1.2 (resource_gate) · хост-тест демона.
- **FR-34 · MUST** · Рестарт процесса ТОЛЬКО через init-скрипт (`fork/exec sh <script> restart`),
  НИКОГДА сигналом — гонка с procd-respawn. · v1.2 · ревью/хост-тест.
- **FR-35 · MUST** · fresh-гейт: процесс моложе grace (возраст из pidfile) → полный grace + сброс
  состояний, В НАЧАЛЕ тика — иначе двойной рестарт поверх procd-respawn. · v1.2 G3 (grace 40→90,
  fresh-гейт) · хост-тест.
- **FR-36 · MUST** · Выздоровление (пульс вернулся / счётчик пошёл) сбрасывает лестницу на
  ступень 0 и счётчики попыток. · v1.2 (pulse_back/progress_back) · хост-тест.
- **FR-37 · MUST** · Py-супервизор ограничивает СВОЙ цикл пересоздания: после
  `max_consecutive_start_failures` падений фабрики подряд ПЕРЕСТаёт пересоздавать сервис
  (громкий лог), передавая эскалацию наблюдателю (сервис молчит → L1-лестница → рестарт
  процесса). Без этого падающая фабрика (напр. `address in use`) крутит backoff-цикл вечно.
  · ревью-итер.8 + ext supervisord startretries→FATAL + v1.2 G3 (порт 1111) · тест: фабрика,
  падающая N раз подряд, останавливает пересоздание, не крутит бесконечно. → конфиг `supervisor.max_consecutive_start_failures`.
- **FR-38 · MUST** · Рестарт процесса — встроенный глагол `restart_process`, целящий в
  процесс-ВЛАДЕЛЕЦ (из контекста вложенности сервиса); мис-адресация в чужой процесс структурно
  невозможна. Механизм и лимит — на процессе (`launch.type` / `launch.restart_rate_limit`); `stop`
  на нём запрещён (бокс без оператора не сдаётся). · ревью-итер.8 (3 линзы: кросс-процессный промах)
  · валидатор (правила 3, 12) + хост-тест (2 процесса: silence vision → рестарт vision, не unified).

## F. Расширение

- **FR-40 · MUST** · Новый вид сигнала/пробы/действия/транспорта/старта = новый ФАЙЛ-адаптер +
  строка `type` в конфиге; core/runtime НЕ правятся. · дизайн-принцип · extension-тест Э3
  (дифф core пуст после добавления нового type).
- **FR-41 · MUST** · Регистрация адаптеров — по имени type (реестр), НЕ хардкод-switch в core.
  · дизайн-принцип · греп: в core нет ветвлений по конкретным type.
- **FR-42 · MUST NOT** · core НЕ содержит имён сервисов/путей/портов/ОС-вызовов.
  · дизайн-принцип · греп Э2 DoD.

## G. Наблюдаемость

- **FR-50 · MUST** · Каждая строка лога наблюдателя несёт `up=<монотонные_сек>` (wall-clock на
  боксе прыгает от time_sync/RTC). · v1.2 G3 finding #6 · греп формата строки.
- **FR-51 · MUST** · Два журнала: событий наблюдателя (проблемы+развязки) и рантайма процесса
  (traceback/старты) — раздельные владельцы ротации, корреляция по up/wall. · v1.2 · ревью.
- **FR-52 · MUST** · Лог — на энергонезависимый носитель (SD), НЕ в tmpfs(/tmp=RAM): читается
  после ребута. В /tmp — только нулевые файлы-флаги. · [[rut-tiny-ram-tmpfs]] v1.2 · ревью пути.

## H. Тестируемость

- **FR-60 · MUST** · Каждый контракт (Transport/Probe/StartMechanism/ActionExecutor) имеет
  in-memory реализацию первого класса; core тестируется без ОС на симулированном времени.
  · потребитель B + ext trio · контрактные тесты Э2 ×2 реализации.
- **FR-61 · MUST** · Тест-хуки — часть протокола (mute-файл, hang-файл, env-подмена /proc),
  документированы, не заглушки в проде. · v1.2 (PROTOCOL.md) · ревью.

## I. Зависимости

- **FR-70 · MUST** · Библиотека и демон — STDLIB-only (на боксе нет pip-пакетов); демон — только
  libjson-c (резидентна). Внешние async-фреймворки (trio/anyio/tenacity) — ПРИНЦИПЫ, не импорты.
  · [[soc-...]] v1.2 · греп импортов.
- **FR-71 · MUST** · Совместимость с версией питона на боксе: НЕ использовать 3.11-only
  (`asyncio.TaskGroup`, `except*`); владение задачами — на 3.9-совместимом коде. · v1.2 · py_compile целевой версией.

### Явно проверенные кандидаты
- **restart intensity (N-за-T)** → в конфиге НЕТ → добавляем `actions.*.rate_limit` (GAP-1). ✅
- **готовность событием vs grace_ms** → grace угадан → типизируем `launch.grace` (GAP-2). ✅
- **порядок старта/остановки сервисов** → наши независимы → НЕ добавляем (боундэри FR-41).
- **clock-инъекция** → контракт core (FR-22), не ключ. ✅
- **SIGTERM посреди флеша** → процесс гасит procd (term_timeout 10с), наблюдатель видит смерть+
  respawn+grace; teardown bounded (FR-14). Отдельного ключа не нужно; поведение задокументировано.
