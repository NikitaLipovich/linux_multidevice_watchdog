# PROTOCOL.md — транспорт и формат сигналов `text_v1` (watchdog v2)

## Канал

Unix-датаграммный сокет (`framework.transport.socket`, боевой `/var/run/svc_wd.sock`).
Наблюдатель создаёт (unlink → bind → `chmod 0666` — отправители могут быть не-root),
отправители шлют `sendto()` без соединения. Датаграмма = одно сообщение, доставка
best-effort: потеря ОДНОЙ датаграммы не событие (пороги ≥ 3× периода отправки).
Контракт отправителя: **emit никогда не кидает исключений** (горячий путь каждого
цикла сервиса; нет сокета/слушателя — сообщение молча пропадает, сервису всё равно).

## Формат `text_v1` — три формы одной ASCII-строки (без \0, без \n)

| Форма | Пример | Смысл |
|---|---|---|
| `<service>` | `udp_logger` | **pulse**: «мой цикл крутится». Обновляет last_seen |
| `<service> <state>` | `config_server idle` | pulse + смена состояния |
| `<service> <state> <counter>` | `config_server active 1042` | pulse + состояние + **activity-счётчик** |

Поля разделены одиночным пробелом. `service` ≤ 47 байт (ёмкость C: NAME 48);
`state` ≤ 23 байт (STATE 24); `counter` — int64 десятичный (≤ 20 символов со знаком).
Максимум легальной датаграммы: 47+1+23+1+20 = 92 байта; приёмный буфер 128 (запас;
более длинное усекается ядром и почти наверняка уходит в unknown-лог).

**ЕДИНОЕ ГЛОБАЛЬНОЕ ПРОСТРАНСТВО ИМЁН (итер.8):** датаграмма несёт ТОЛЬКО `<service>` — БЕЗ
квалификатора процесса. Значит имя сервиса обязано быть уникально ГЛОБАЛЬНО по всем процессам
(валидатор правило 7): два сервиса с одним именем в разных процессах слепили бы `last_seen` и
общий crash-файл `/tmp/svc_crash_<service>`, и наблюдатель не смог бы адресовать пульс/тишину.
`last_seen` и файлы-запросы ключуются именем сервиса, не парой (процесс,сервис).

## Словарь состояний (протокольные слова)

- `active` — рабочая операция идёт; ТОЛЬКО в этом состоянии судится L2.
- `idle` — рабочая операция кончилась (**закрывает эпизод L2**); шлётся из finally
  рабочего кода — умер без idle → счётчик замрёт при active → L2 сработает (желаемое).
- Другие слова разрешены (демон хранит и логирует смену), но семантики уровней не несут.

## Семантика на стороне наблюдателя

- **pulse** (любая форма, ВКЛЮЧАЯ форму-3 с counter): `last_seen[service] = now`. Тишина дольше
  `watch.L1_pulse_lost.dead_after_ms` → уровень L1 сработал. Примечание (итер.8): датаграмма
  `activity` (форма-3) ТОЖЕ обновляет `last_seen` — это НЕ дыра: она приходит из реально
  исполняющегося рабочего кода (флеш крутится), что доказывает жизнь СИЛЬНЕЕ, чем probe порта.
  Probe-гейт (уровень 1.5) нужен только базовому пульсу `from:"probe"` (у него нет своего кода-
  доказательства); у `from:"loop"` и у activity доказательство — сам факт исполнения.
- **watch-уровни — ЗАКРЫТОЕ множество** (валидатор правило 16): сервис `{L1_pulse_lost,
  L2_activity_frozen}`, процесс `{P1_all_pulses_lost, P2_request_stuck}`. Ключ уровня — метка,
  которую C-ядро связывает с зашитым компаратором; неизвестный ключ = отказ (не «открытый» словарь).
- **ready** (форма-2, `<process> ready`) — ОПЦИОНАЛЬНО, задел Э5: процесс объявляет готовность
  после старта → `grace.type:"until_ready"` кончает слепоту РАНЬШЕ `max_ms`. Пока не реализовано;
  `until_ready` без объявленного ready-сигнала валидатор отвергает (правило 13).
- **state**: смена значения логируется (дедуп по значению, НЕ rate-limit); смена
  закрывает эпизод L2.
- **counter**: первый counter-пульс открывает эпизод; изменение значения =
  `last_progress = now`. Эпизод ∧ state==`active` ∧ counter замер дольше
  `frozen_after_ms` → уровень L2 сработал. Значение счётчика непрозрачно — судится
  только «менялся или нет». Сброс эпизода: смена state, исполнение recreate по этому
  сервису, рестарт процесса, fresh-гейт.
- Имя не из конфига → `unknown`-лог (rate-limit `observer.quiet.unknown_ms`).

## Кто что излучает (соответствие `signals` конфига)

- `signals.pulse from:"loop"` — рабочий цикл сервиса зовёт emit сам (форма 1).
- `signals.pulse from:"probe"` — корутина библиотеки: probe (напр. TCP-connect на
  `@port` с `timeout_ms`) → успех = emit, провал = НЕ слать (молчание увидит L1).
- `signals.activity` — рабочий код зовёт tick() на каждой итерации; библиотека
  троттлит до 1 датаграммы в `tick_ms` (форма 3, state=`active`); конец работы —
  emit `idle` (форма 2). Значение `tick_ms` передаётся рабочему коду ПАРАМЕТРОМ
  (нарезка его ожиданий) — рабочий код конфиг не читает.

## Действия (протокольные константы исполнения)

- `request_file`: creat(файл из шаблона, {service} подставлен), mode 0644; потребление =
  unlink супервизором. Не съеден за `eat_within_ms` → сигнал P2_request_stuck.
- `init_script`: `fork` → `execl("/bin/sh", "sh", <launch.script процесса>, "restart")`.
  Глагол `restart` фиксирован. Сигналы процессу запрещены (гонка с procd).

## Журнал наблюдателя (формат строки)

`<wall-ISO-время> up=<монотонные_сек> <событие> k=v …` — `up=` обязателен: wall-clock
на боксе прыгает (time_sync/RTC), порядок событий читается только по up.

## Тест-хуки (протокольные, вне конфига)

- `/tmp/wd_test_mute_<service>` — существует → emit этого сервиса молчит (симуляция
  тихой смерти без остановки сервиса).
- `/tmp/wd_test_hang` — существует → потребитель A блокирует весь event loop на 90с
  (инъекция P1_all_pulses_lost).
- env `WD_PROC_MEMINFO` / `WD_PROC_LOADAVG` — подмена /proc-файлов для хост-тестов гейтов.
- env `WD_CONFIG` — путь конфига (bootstrap, py-сторона; C — argv[1]).
